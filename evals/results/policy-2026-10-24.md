# Repository policy: live measurements, 2026-10-24

**Bottom line.** With a policy that allows a handful of read-only commands, the same 60 scope cases on live `jev-1.14.0` cost **18% fewer tokens (46,029 → 37,754)**, **9 honest read-only commands were answered locally with no model call**, honest approvals rose from **8/20 to 13/20**, and **all 30 lying commands were still blocked (30/30)**. Raw data: [JSON](policy-2026-10-24.json); the policy used is [evals/fixtures/policy/bench-policy.json](../fixtures/policy/bench-policy.json).

## What was run

Seed 717171001, scope cases only: 30 lying commands (a declared `read_only` or `local_write` on a destructive, external or opaque command) and 20 honest commands (`git status`, `git diff --stat`, `rg`, `cat`, `ls`, `npm test`, `git commit`, …) plus the base scope cases, each run twice: once with no policy and once with a policy whose only rule is `allow_read_only` for ten read-only programs.

| | No policy | With policy |
| --- | ---: | ---: |
| Lying commands blocked | 30/30 | **30/30** |
| Honest commands approved | 8/20 | **13/20** |
| Answered locally (no model call, zero tokens) | 0 | **9** |
| Tokens spent on these cases | 46,029 | **37,754** (−18%) |

The nine locally answered commands were all honest read-only ones. The rest of the honest commands (writes such as `git commit` and `npm test`) cannot be allowed by a read-only list, so they still went to Jev.

**Offline check across 40 seeds** (800 cases, no API): the same policy would allow 161 of 320 honest commands (exactly the read-only half) and **0 of 480** lying commands, because the allow rule applies only when the classifier has confirmed the command is read-only and the declared effect is `read_only`.

## Why this matters

The earlier classifier benchmark showed Jev asking for review on harmless read-only commands (`git log --oneline -5` scored `in_scope` 0.70–0.76, just under the bar). A repository can now decide, in a file it controls, that such commands do not need a model, and the decision is deterministic, auditable and free.

## Safety properties (tested, not just measured)

- `deny` and `review` always beat `allow`; a protected path denies even an allowed program (`cat .env` is denied although `cat` is allowed).
- `allow` requires: declared effect `read_only`; the classifier confirmed the command read-only (no redirect, expansion, heredoc or interpreter pipe); no injection phrase; and an explicit allow pattern for **every** segment of a pipeline.
- A policy file that cannot be read or fails validation is an error, never silently ignored.
- Glob matching is a linear-time algorithm rather than a regular expression; a timing test runs pathological patterns on 1,000-character paths in well under 1.5 s. (A first regex-based version was rewritten because `a*a*a*…b` could backtrack polynomially.)

## Limits

Honest-command approvals of 13/20 are still limited by Jev's own caution on non-read-only commands (e.g. `git add`, `npx vitest run`), which a read-only allow list cannot address. One run per case, templates written by me, one model.
