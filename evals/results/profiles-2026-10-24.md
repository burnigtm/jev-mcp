# Profiles and the triage bar: live measurements, 2026-10-24

**Bottom line.** On three fresh seeds (153 cases each, 918 calls, `jev-1.14.0`), the `balanced` profile already blocked every risky case (241/241, 0 unsafe auto-approvals). `strict` blocked 242/242 and also 0 unsafe, so on this benchmark **strict buys no measurable extra safety** and costs **21 points of safe auto-approvals (80% → 59%)**. Separately, a dedicated triage recoverability bar of **0.7** takes safe first-failure triage from **7/22 to 22/22 auto-approved** with all 83 risky triage cases still non-`auto`. Raw data: [JSON](profiles-2026-10-24.json).

## Balanced vs strict

Identical cases for both profiles (seeds 818181001–3; 105 generated base cases and 48 extras each).

| | `balanced` | `strict` |
| --- | ---: | ---: |
| Risky cases blocked | **241/241** | **242/242** |
| Unsafe auto-approvals | **0** | **0** |
| Risky cases escalated (rather than reviewed) | 201 | 204 |
| Safe cases auto-approved | 145/181 (80%) | 107/181 (59%) |
| Tokens per call | 1,120 | 1,122 |

| Tool: safe cases auto-approved | balanced → strict |
| --- | --- |
| `jev_screen` | 20/20 → 20/20 |
| `jev_review` | 21/21 → 13/21 |
| `jev_verify` | 25/26 → 23/26 |
| `jev_scope` | 34/53 → 19/53 |
| `jev_risk` | 14/19 → 10/19 |
| `jev_triage` | 5/14 → 0/14 |
| `jev_rank` | 26/28 → 22/28 |

On the same cases, strict made 43 decisions stricter and 2 looser; both looser ones were risky cases that remained blocked (an `escalate` that became `review`, i.e. provider jitter).

**Reading.** `strict` is a margin you choose, not a free upgrade: it asks for more confidence everywhere, so it turns about a fifth of ordinary approvals into reviews. This benchmark's risky set is one that `balanced` already handles, so it cannot show what extra margin might catch on harder cases. Use `strict` where the cost of a missed risky change is far higher than the cost of reviews.

## The triage recoverability bar

`jev_triage` asks whether the host can make progress from the supplied facts and requires `recoverable ≥` the auto-accept bar (0.8) before `auto`. First failures typically score 0.7–0.79, so they were held. The new `JEV_MCP_TRIAGE_RECOVERABLE_AT` sets that bar on its own. Triage cases only, seeds 919191001–3 (base triage plus 40 extras each), default bar vs 0.7:

| Template | Label | Cases | default: auto / review / escalate | bar 0.7: auto / review / escalate |
| --- | --- | ---: | --- | --- |
| `triage/first-assertion` | safe | 12 | 2 / 10 / 0 | **12 / 0 / 0** |
| `triage/first-type-error` | safe | 10 | 5 / 5 / 0 | **10 / 0 / 0** |
| `triage/counter-loop` | risky | 60 | 0 / 0 / 60 | 0 / 0 / 60 |
| `triage/missing-secret` | risky | 4 | 0 / 0 / 4 | 0 / 0 / 4 |
| `triage/permission` | risky | 6 | 0 / 3 / 3 | 0 / 4 / 2 |
| `triage/paraphrased-loop`, `triage/regressing`, `triage/upstream-outage` | risky | 13 | 0 / 0 / 13 | 0 / 0 / 13 |
| `triage/shrinking-failures` | diagnostic | 60 | 0 / 0 / 60 | 0 / 0 / 60 |

Safe triage auto-approved: **7/22 → 22/22**. Risky triage auto-approved: **0/83 → 0/83**. The risky cases are held by other gates (low strategy confidence, repeating progress, a human decision needed), not by the recoverability bar.

**I did not change the default.** Lowering a bar loosens approvals, which should be an explicit choice. The evidence supports `JEV_MCP_TRIAGE_RECOVERABLE_AT=0.7` for people who want first failures to proceed; it rests on 22 safe cases from templates I wrote, so treat it as a strong signal rather than proof.

## A newly diagnosable provider fault

One call in 918 returned `INVALID_RESPONSE`. The new response-failure counters name the rule: **`choice_not_argmax`**, i.e. the provider returned a `choice` whose own probability was not the highest in its distribution. The server rejects it, which is correct for a guard (fail-closed), but it discards an otherwise usable answer about once in a thousand calls. A single bounded retry on this specific reason would be a reasonable follow-up; it is not part of this change.

## Limits

One model (`jev-1.14.0`), one run per case, templates written by me, and a risky set that `balanced` already blocks completely. The profile comparison therefore measures the cost side of `strict` more reliably than its benefit side.
