# Pull-request gate: dry run on this repository's own history, 2026-10-24

**Bottom line.** `jev-mcp ci` was run against three pull requests this repository already merged (#12, #13, #14), with the real title and body of each and live `jev-1.14.0`. With default settings it would have **failed #12 and #13 (exit 20, `escalate`)** and let #14 through only because that one was run without a model (it is 26,696 added lines, mostly benchmark data). That is a strict gate, not a calibrated one: treat the first weeks as advisory (a non-required check, or `--fail-on escalate`) and read the held parts before turning it into a required check. Raw data: [JSON](ci-2026-10-24.json).

| --- | ---: | --- | --- | ---: | --- |
| #12 scope, triage and risk tools | 33 | Jev | `escalate` (exit 20) | 3 | patch review: both chunks `escalate` (22 and 11 files); security review: both `review` |
| #13 guardrail hardening | 34 | Jev | `escalate` (exit 20) | 3 | patch review: all 3 chunks `escalate` (20, 10 and 4 files); security review: all 3 `review` |

Each run took about 1.5 to 2 s, three tool calls (a screen of the description, a patch review and a security review; the last two are chunked when the diff needs it).

## What held them

- **Jev's own caution on large patches.** Chunk-level reasons were `unsafe_to_apply`, `correctness_uncertain`, `spec_match_uncertain`, `safe_to_apply_uncertain` and `composite_low`, the same pattern as the large-diff benchmark: Jev rarely approves a big change it cannot run.
- **The deterministic floors**, as designed: `unpaired_source_change` and `export_signature_change` on both, `lockfile_changed` on #12.
- **`injection_in_pr_text` on both, which is a false positive here.** Both pull requests are about the injection backstop and quote the phrases it catches (for example `ignore your previous instructions`, spelled out and with a hidden character). The result for text like that is a hold for review, not a block, and the summary says why. A repository that writes about prompt injection will see this.
- **`secret_in_diff` on #12**: one secret-shaped string in the diff (a test fixture). It was redacted before anything was sent; the hold stays.

## A defect the dry run found

The first run held both pull requests for `claims_unsupported`: with no checked boxes in the description the gate invented the claim "the change implements what was requested" and then could find no evidence for it. When nothing is claimed, the gate now reviews the patch and its security without verifying any claim; claims come only from checked boxes (`- [x] ...`) in the description, and are verified against the log supplied with `--tests-file`. The same change fixes the `Stop` hook, which had the same default.

## Limits

Three pull requests, one run each, all of them from this repository and all large. This says how strict the gate is on big changes by default, not how often it is right. It did not run inside GitHub Actions (the example workflow is untested there), and the check was not run against a pull request from a fork.
